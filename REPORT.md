## Мета роботи

Упакувати інференс-сервіс аудіокласифікатора з ЛР №1 у відтворюваний Docker-образ,
розділити навчання й виконання через multi-stage build, порівняти розгортання в контейнері
та без нього, налаштувати базовий CI із quality gate за accuracy.

## 1. Модель і датасет

- **Датасет:** Google Speech Commands v0.02 (16 кГц, 1 с). Класи: `yes`, `no`, `up`, `down`.
  Розбиття — офіційні `validation_list.txt` / `testing_list.txt`.
  Розміри вибірок: train ⟨n_train⟩, test ⟨n_test⟩ (з `metrics.json`).
- **Препроцесинг** (`src/data.py`, однаковий для навчання та API): моно → ресемплінг до 16 кГц →
  обрізання/доповнення до 16000 відліків → MelSpectrogram (n_fft=400, hop=160, 64 мел-смуги) →
  AmplitudeToDB → нормалізація per-sample. Вхід моделі: 1×64×101.
- **Архітектура** (`src/model.py`): 4 блоки Conv3×3–BatchNorm–ReLU–MaxPool (16→32→64→64 канали) →
  Global Average Pooling → Dropout(0.2) → Linear(64→4). Параметрів: ⟨num_params⟩.
- **Навчання:** AdamW (lr=1e-3, wd=1e-4), CosineAnnealing, batch 128, 10 епох, seed 42;
  зберігається найкраща за val-accuracy епоха.

## 3. Dockerfile (multi-stage) — пояснення

| Рядки | Що робить і навіщо |
|---|---|
| `FROM python:3.10-slim AS trainer` | легкий базовий образ (~120 МБ замість ~1 ГБ у `python:3.10`) |
| `apt-get install libsndfile1 … rm -rf /var/lib/apt/lists/*` | системна бібліотека для `soundfile`; кеш apt видаляється в тому ж шарі |
| `COPY requirements-train.txt` + `pip install --no-cache-dir` | залежності окремим шаром → кешуються, поки не змінився requirements |
| `RUN … SPEECHCOMMANDS(download=True) && rm *.tar.gz` | датасет — окремий шар **до** копіювання коду: зміна `train.py` не викликає повторного завантаження 2.3 ГБ |
| `COPY src/` | код — після важких шарів |
| `ARG EPOCHS/SEED/MODEL_VERSION` + `RUN python -m src.train` | навчання під час збірки, параметри фіксовані для відтворюваності; у CI `EPOCHS=3` |
| `FROM python:3.10-slim AS runtime` | новий чистий етап: датасет, tqdm, scikit-learn сюди не потрапляють |
| `LABEL org.opencontainers.image.*` | OCI-мітки: версія моделі, git-коміт, дата збірки |
| `pip install -r requirements-api.txt` | лише інференсні залежності, CPU-збірка torch |
| `COPY --from=trainer /build/artifacts` | з етапу trainer переходить **тільки** model.pt, labels.json, metrics.json |
| `ENV MODEL_PATH, PORT, LOG_LEVEL …` | конфігурація через змінні середовища |
| `useradd appuser` + `USER appuser` | процес не від root |
| `EXPOSE 8000` | документує порт (публікація — через `-p` при запуску) |
| `HEALTHCHECK … /health` | Docker сам перевіряє стан → статус `healthy`/`unhealthy` |
| `CMD ["sh","-c","exec uvicorn …"]` | `exec` робить uvicorn PID 1 → коректна обробка SIGTERM |

`.dockerignore` і `requirements-*.txt` — див. файли в репозиторії (вставити вміст у звіт).

## 9. Відповіді на контрольні питання

**1. Образ vs контейнер, шар.** Образ — незмінний шаблон зі стеку шарів read-only; контейнер — запущений екземпляр образу з власним записуваним шаром зверху, процесами, мережею. Шар — набір змін файлової системи, створений однією інструкцією (`RUN`, `COPY`, `ADD`); шари кешуються і спільно використовуються різними образами.

**2. .dockerignore.** Визначає, які файли не передаються демону в build context. Без нього `docker build` відправлятиме `.git`, `.venv`, датасет (гігабайти) — збірка повільна, кеш `COPY .` інвалідовується від будь-якої зміни, у образ можуть потрапити секрети й сміття.

**3. Порядок інструкцій і кеш.** Docker перевикористовує шар, якщо інструкція і її вхід не змінилися; після першого зміненого шару всі наступні перезбираються. Тому рідко змінюване (базовий образ, apt, requirements, датасет) — на початку, часто змінюване (код) — в кінці.

**4. Multi-stage build.** Розв'язує проблему «важкого» фінального образу: інструменти збірки/навчання, датасет і проміжні файли лишаються в проміжних етапах. У фінальний образ потрапляє тільки те, що явно скопійовано `COPY --from=…` (тут — model.pt, labels.json, metrics.json), плюс runtime-залежності.

**5. CMD vs ENTRYPOINT, EXPOSE vs -p.** `ENTRYPOINT` — фіксована виконувана команда, `CMD` — команда/аргументи за замовчуванням, які легко перевизначити в `docker run <image> …` (з ENTRYPOINT — це аргументи до неї). `EXPOSE` лише документує порт у метаданих образу; `-p host:container` реально публікує порт на хості.

**6. CPU-збірка PyTorch.** Пакет із CUDA в рази більший (≈2.5 ГБ проти ≈200 МБ wheel), а легка CNN на CPU вже дає мілісекундну latency; GPU на сервері інференсу часто немає. Менший образ — швидше завантаження, старт, менше CVE.

**7. Модель в образі vs на volume.** В образі: один відтворюваний артефакт, версія коду і моделі зв'язані, простий деплой; але кожна нова модель — перезбирання образу і більший образ. На volume: оновлення моделі без перезбирання, менший образ, одна модель для кількох реплік; але треба окремо версіонувати модель, можлива розбіжність коду й моделі, залежність від сховища.

**8. HEALTHCHECK.** Дає Docker-у спосіб перевіряти, що сервіс реально працює (а не лише процес живий). Compose використовує його в `depends_on: condition: service_healthy`; у Kubernetes аналог — liveness/readiness/startup probes: невдалий liveness → перезапуск pod, readiness → pod виключається з балансування.

**9. Не від root.** Root у контейнері — це root ядра хоста (без user namespaces); при вразливості в застосунку чи runtime зловмисник отримує більше можливостей для втечі з контейнера, запису в змонтовані volume тощо. Принцип мінімальних привілеїв.

**10. Різниця latency.** На Linux контейнер — звичайний процес з namespaces/cgroups, тому обчислення не сповільнюються. Різниця виникає через мережу (docker-proxy/NAT для `-p`), обмеження cgroups (`--cpus`), інші версії бібліотек (MKL/OpenMP) і, на macOS/Windows, через VM. Зазвичай вона несуттєва (долі мілісекунди) порівняно з самим інференсом і мережею клієнта.

**11. Docker у CI/CD для ML.** Образ збирається на кожен коміт із тегом = git sha, у CI запускається контейнер, проходять smoke-тести і quality gates (accuracy, latency); лише після успіху образ публікується в реєстр і розгортається (Kubernetes, SageMaker, Vertex AI). Те, що перевірено в CI, — рівно той артефакт, що піде в production.
